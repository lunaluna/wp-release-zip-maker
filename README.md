# wp-release-zip-maker

GitHub の Release を使えないプロジェクト(クライアントワークなど)でも、テーマ・プラグイン・
WordPress の外のディレクトリの配布用 Zip を、**ローカルで・版を管理しながら**作るコマンドです。

## 何をするか

- サーバーでは Git を使いません。テーマ・プラグインは管理画面の Zip アップロード、ディレクトリは SSH で上げて unzip します
- 1 つのリポジトリにテーマとプラグインなど複数のものが入っていても、それぞれの Zip を作れます
- Zip の作成は WP-CLI の公式パッケージ `wp dist-archive` に任せます。このツールは git と版の管理を担う薄いラッパーです
- 版のタグは素の版番号です(`v` を付けません)。Zip は HEAD(または既存のタグ)のコミットから作るので、作業ツリーの途中の状態が混ざりません
- 事前に、止めるべき状態(作業ツリーが汚れている・版の表記がそろっていない・タグや Zip がすでにある、など)を確かめ、理由を示して止めます

### このツールがしないこと

- `git push` はしません(タグを共有するコマンドを表示するだけです)
- サーバーへのアップロードはしません(手順を表示するだけです)
- 版の書かれたファイルを書き換えません(版は、あなたが上げてコミットします。このツールは読んで確かめるだけです)
- GitHub の Release は作りません
- 鍵・署名は扱いません(`--sign` は Git の `git tag -s` に任せます。Zip やマニフェストそのものへの署名(`.asc` など)は作りません)
- WordPress・データベースには接続しません。ネットワークにも接続しません(`git` と `wp` を呼ぶだけです)
- Zip を上書きしません(すでにあれば止めます)

## 必要なもの

- bash(macOS 標準の 3.2 で動きます)
- git・`zip`
- WP-CLI と、そのパッケージ `wp-cli/dist-archive-command`
- `unzip`: Zip の中身の確認(配布してはいけないファイルの検査を含む)・内容の指紋・サマリーの内訳に使います。**無ければ止まります**(build・`--rebuild`・それぞれの `--dry-run`. `--list` は Zip を扱わないので動きます). 1.1.0 までは、無ければ検査を省いて警告するだけでした

`wp dist-archive` の入れ方は、WP-CLI の版によって変わります。

```bash
wp package install wp-cli/dist-archive-command:3.1.0   # WP-CLI 2.12.x(この版で確かめた)
```

版を指定せずに入れると、WP-CLI 2.12.x では失敗します(最新版が WP-CLI 3.0 以上を要求するため)。
WP-CLI 2.13 以上では、版を指定せずに入れられる見込みですが、**未確認**です(2.12.0 でだけ確かめました)。

## インストール(Mac に 1 回だけ)

プロジェクトにツールのコードは入れません。clone して、PATH の通ったところへシンボリックリンクを張ります。

```bash
git clone https://github.com/lunaluna/wp-release-zip-maker.git ~/private/wp-release-zip-maker   # 置き場所は自由
mkdir -p ~/.local/bin
ln -s ~/private/wp-release-zip-maker/bin/wp-release-zip-maker ~/.local/bin/wp-release-zip-maker
wp-release-zip-maker --version      # 版が出れば、PATH が通っています
```

更新は、clone したディレクトリで `git pull` します。プロジェクトに置くのは、設定ファイル `.wp-release` と、各対象の `.distignore` だけです。

- `main` は、リリースのときにだけ進みます(作業はブランチで進め、リリースのときに `main` へマージします)。`git pull` で取れるのは、いつも最新のリリースです
- 新しい版が出たことを知るには、GitHub のリポジトリの **Watch → Custom → Releases** を選んでください。リリースのたびに GitHub の Release(1.1.0 から)を作るので、通知が届きます
- 版を固定したいときは、タグを取り出します(`git -C ~/private/wp-release-zip-maker checkout 1.1.0`)。最新に戻すには `git checkout main` のあとで `git pull` します
- フォークや Release からのダウンロードは要りません(更新を受け取りにくくなります)

## クイックスタート

1. Git のルートに、設定ファイル `.wp-release` を置く(見本: [examples/](examples/))
2. 配布する各ディレクトリに、Zip に入れないものを書いた `.distignore` を置いて、コミットする
   (`wp dist-archive` は `.distignore` が無いと、`node_modules` や `src` も含む全ファイルを入れるため、無ければ止めます)

   ```text
   .distignore
   .git
   .gitignore
   node_modules
   src
   package.json
   package-lock.json
   ```

3. `wp-release-zip-maker --list` で、対象と版・タグの有無を確かめる
4. 版を上げてコミットする(版の表記を複数のファイルに持つなら、`check` の行で、そろっているか確かめられます)
5. `wp-release-zip-maker <slug> --dry-run` で確認し、`wp-release-zip-maker <slug>` で Zip とタグを作る
6. 必要なら、タグを共有する(`git push <リモート名> <タグ>`)
7. 表示された手順で、Zip をサーバーへ上げる

## 使い方

```text
wp-release-zip-maker <slug>                    # HEAD から Zip を作り、注釈付きタグを打つ(push はしない)
wp-release-zip-maker <slug> --sign             # 署名付きのタグ(git tag -s)を打つ(gpg と鍵が要る)
wp-release-zip-maker <slug> --dry-run          # 確認だけ(Zip もタグも作らない)
wp-release-zip-maker <slug> [--rebuild [<版>]] --dry-run --verify-content   # Zip を一時ディレクトリに作って中身まで確かめ、消す
wp-release-zip-maker <slug> --rebuild [<版>]   # 既存のタグの時点から Zip だけを作り直す(タグは打たない)
wp-release-zip-maker <slug> --rebuild [<版>] --allow-content-change   # 内容の指紋がタグの記録と違っても続ける
wp-release-zip-maker <slug> [--rebuild [<版>]] --manifest             # Zip のファイルごとの SHA-256 の一覧も作る
wp-release-zip-maker <slug> [--rebuild [<版>]] --json <パス>          # 機械が読める JSON のレポートも作る
wp-release-zip-maker --list                    # 設定にある対象と、今の版・タグの有無を一覧にする
wp-release-zip-maker --version / --help
```

`--dry-run` と `--rebuild` は組み合わせられます(`<slug> --rebuild --dry-run` は、作り直しの確認だけ)。
終了コードは、0 = 成功、1 = 事前の確認などで止めた(利用者が直せるもの)、2 = 使い方の誤りです。

## 設定ファイル `.wp-release`

カレントディレクトリから上へ探します(Git のルートで止めます)。Git の外では動きません。
見本は [examples/](examples/) にあります(docroot 型・プラグイン 1 つ型)。

```text
tag_format = {slug}/{version}        # 省略可。対象が 1 つなら {version}、複数なら {slug}/{version}
output     = ../releases             # 必須。設定ファイルからの相対パス。Git と docroot の外を推奨
requires   = 1.0.0                   # 省略可。このツールの最低の版。古ければ止める
max_zip_bytes          = 20M         # 省略可。Zip の大きさの上限(下の「大きさの上限」)
max_files              = 500         # 省略可。Zip の中のファイルの数の上限
max_uncompressed_bytes = 50M         # 省略可。展開したときの合計の大きさの上限

# 種類    パス(設定ファイルからの相対)    スラッグ(省略時はディレクトリ名)
plugin   wp-content/plugins/my-plugin
theme    wp-content/themes/my-theme
dir      lp                              # スラッグを省くと、ディレクトリ名(lp)になる

# 版の表記がそろっているかの追加の確認(任意)。check パス:正規表現
check    wp-content/plugins/my-plugin/package.json:"version"
```

- `#` で始まる行と、空白の後ろの `#` 以降はコメントです(`check` の正規表現には、空白のあとに `#` を続けて書けません)
- パスは設定ファイルからの相対パスです。絶対パスと `..` は使えません。パス `.` はスラッグの省略ができません
- スラッグは英数字・ドット・ハイフン・アンダースコアだけです(先頭のドットは不可)。対象どうしで重複できません
- **スラッグは、ディレクトリ名(サーバーに置く名前)と同じにすることを基本とします。** ふつうはスラッグを省けば、ディレクトリ名になります。
  理由: スラッグは、Zip の一番上のフォルダー名と、サーバーで置き換える先の名前を決めるためです(下の「スラッグとディレクトリ名」)
- 対象が複数あるときは、`tag_format` に `{slug}` を含めます(別の対象のタグが衝突するため)
- `output` は省略できません(省略時の置き場所を決めると、Git の中に Zip を作る事故につながるため)
- **大きさの上限(`max_zip_bytes`・`max_files`・`max_uncompressed_bytes`)は、どれも省略できます。既定は「上限なし」で、書いたものだけ確かめます**(下の「大きさの上限」)
- `check` は、そのパスを含む対象(`plugin`/`theme`/`dir` のディレクトリの下)の確認にだけ使います。
  たとえばプラグインとテーマの両方が入る設定で、プラグインの Zip を作るときに、テーマの `package.json` とは比べません。
  どの対象の下にもない `check` は、書き間違いとして止めます

### スラッグとディレクトリ名

**スラッグは、ディレクトリ名(サーバーに置く名前)と同じにすることを基本とします。**
スラッグは、Zip の名前とタグ名のほかに、次の 2 つを決めます。ディレクトリ名と違うと、サーバーで置き換わる先がずれます。

| 種類 | スラッグで決まるもの | ディレクトリ名と違うと |
| --- | --- | --- |
| `plugin` / `theme` | Zip の一番上のフォルダー名。管理画面からアップロードすると、WordPress はこの名前のフォルダーに置きます | 既存のものを置き換えず、**別のプラグイン・テーマとして入ります**(同じものが 2 つになり、有効化し直しが要ります) |
| `dir` | Zip の一番上のフォルダー名と、表示する SSH の手順で置き換える場所(`$DOCROOT/<slug>`) | 手順のとおりに実行すると、**別の名前(別の URL)に置かれ**、元のディレクトリの旧版は退避されません。手順の `mv` の行き先を、毎回手で直すことになります |

- スラッグを省くと、ディレクトリ名がそのまま使われます。ふつうは省いてください
- 書く必要があるのは、パスが `.` のとき(プラグイン 1 つ型。ディレクトリ名が決まらない)だけです。そのときは、**サーバーで使っているフォルダー名**を書きます
- ディレクトリ名に、スラッグに使えない文字(日本語・空白など)が入っているときは、スラッグを書けません。ディレクトリ名を英数字に変えることを勧めます
- 根拠(`plugin` / `theme`): WordPress 7.1.3 の `wp-admin/includes/class-wp-upgrader.php` の `install_package()` は、置く先を「プラグイン(テーマ)のディレクトリ + Zip の一番上のフォルダー名(`basename( $source )`)」にします

## 動作の詳細

### 大きさの上限(`max_zip_bytes`・`max_files`・`max_uncompressed_bytes`)

誤って大きなファイルが入った Zip(`node_modules` の取り込み・バックアップ・動画など)を、配る前に止めるための確認です。**書いたキーだけ確かめます**(既定は無し)。

| キー | 確かめるもの |
| --- | --- |
| `max_zip_bytes` | Zip のファイルの大きさ(バイト) |
| `max_files` | Zip の中のファイルの数(ディレクトリは数えません) |
| `max_uncompressed_bytes` | 展開したときの合計の大きさ(バイト) |

- 値は正の整数です。末尾に `K`・`M`・`G`(1024 の倍数)を付けてもかまいません(例: `max_zip_bytes = 20M`)。それ以外(0・小数・`20MB` など)は、設定の誤りとして行番号つきで止めます(`--list` でも止まります)
- 設定ファイル全体に 1 組です(対象ごとには持ちません)
- **確かめる場所**: Zip を作って中身を確かめた直後・出力先へ置く前・タグを打つ前です。`--rebuild` も同じです
- **超えたとき**: 終了コード 1 で止めます。出力先に Zip を置かず、タグも打ちません。超えた項目と値・上限・大きいファイルの上位 10 個(展開後の大きさ順)・直下の内訳を表示します。ちょうど上限と同じ値は通ります
- **上限以下のとき**: 要約に「上限: 〜 以下」の行を出します
- 目安にする値は、実際の Zip から決めてください(2026-10-28 に測った例: プラグイン 170KB・72 ファイル・展開後 440KB / テーマ 424KB・107 ファイル・展開後 660KB / 画像の多いディレクトリ 3.5MB・30 ファイル・展開後 3.8MB)。上の例の値は書き方の見本です
- 展開後の大きさは `unzip -Zt` の「N bytes uncompressed」から読みます(読めなければ `unzip -l` の合計の行)。書式は Info-ZIP の版で違う可能性があり、この Mac の `unzip` 6.00 でだけ確かめました。読めなければ、`max_uncompressed_bytes` を確かめられないので止めます
- **1.1.0 以前のツールは、知らないキーで止まります。** 使うなら `requires = 1.2.0` にしてください

### 機械が読めるレポート(`--json <パス>`)

build・`--rebuild` が成功したあと、指定したパスに JSON のファイルを作ります(CI やほかのスクリプトが、Zip の版・指紋を読むためのものです)。

- パスは、カレントディレクトリからの相対パスでも絶対パスでもかまいません。親のディレクトリが無ければ作ります
- **上書きしません。** すでにあれば、Zip もタグも作らずに止めます(`--manifest` と同じ)
- `--dry-run`・`--list` とは使えません(使い方の誤りで、終了コード 2)
- 標準出力に出す形(`--json` だけ)にしないのは、今の表示も標準出力に出ていて、混ざるためです(表示を標準エラーへ移すと、今の使い方が変わります)
- **作れなかったとき**(置き場所に書けないなど): Zip とタグは**消さずに残し**、手順の表示まで進めたあと、警告して終了コード 1 で終わります(メッセージで「Zip とタグは正しくできている」と伝えます)。JSON は記録のためのもので、配布物ではないためです。これは `--manifest`(作れなければ Zip も消し、タグも打たない)と違う扱いです
- jq などに頼らず、シェルだけで書き出します。パスに `"`・`\`・改行があってもエスケープされます(ASCII 以外はそのまま UTF-8 で出します)

```json
{
  "tool_version": "1.2.0",
  "slug": "my-plugin",
  "kind": "plugin",
  "version": "1.2.3",
  "action": "build",
  "tag": "my-plugin/1.2.3",
  "commit": "<コミットのハッシュ(40 桁)>",
  "branch": "main",
  "zip": "/abs/path/my-plugin.1.2.3.zip",
  "bytes": 12345,
  "sha256": "<Zip 全体の SHA-256>",
  "content_sha256": "<内容の指紋(タグの Content-SHA-256 と同じ)>",
  "files": 72,
  "uncompressed_bytes": 450000,
  "manifest": null,
  "signed": false,
  "built_with": { "wp_cli": "2.12.0", "dist_archive": "3.1.0", "zip": "3.0" },
  "created_at": "2026-10-28T16:30:00+09:00"
}
```

| キー | 中身 |
| --- | --- |
| `action` | `build` か `rebuild` |
| `tag` | タグ名(`rebuild` は、作り直す元のタグ) |
| `commit` | Zip の元のコミット(`rebuild` は、タグが指すコミット) |
| `branch` | build のときのブランチ名。detached HEAD と `rebuild` は `null`(`rebuild` はタグの時点から作るため) |
| `sha256` / `content_sha256` | Zip 全体の SHA-256 / 内容の指紋(`rebuild` では前者は毎回変わります。「動作の詳細」の `Content-SHA-256` を参照) |
| `files` / `uncompressed_bytes` | ファイルの数(ディレクトリは数えない)/ 展開後の合計。読めなければ `uncompressed_bytes` は `null` |
| `manifest` | `--manifest` を付けたときはそのパス、付けなければ `null` |
| `signed` | `--sign` を付けたか(`git config tag.gpgSign` による署名は反映しません) |
| `built_with` | Zip を作った道具の版(調べられなければ `"unknown"`) |
| `content_match` | **`rebuild` のときだけ**。タグの記録と内容の指紋が一致したら `true`、違えば `false`(`--allow-content-change` で続けたとき)、記録がなければ `null` |
| `created_at` | ISO 8601(ローカル時刻 + オフセット) |

### 中身まで確かめる(`--dry-run --verify-content`)

`--dry-run` は、Zip を作らずに事前の確認だけをするので、**中身の検査(配布してはいけないファイル・外へ出る名前)と大きさの上限は、実際に作るまで分かりません**。
`--verify-content` を `--dry-run` に付けると、事前の確認がすべて通ったあと、一時ディレクトリに Zip を作り、本番と同じ確認をします。

- 確かめるもの: 中身の検査(`verify_zip`)・大きさの上限・ASCII 以外のファイル名の警告。そのあと、サマリー(大きさ・SHA-256・直下の内訳)を出して、**Zip を消します**
- **出力先・タグ・マニフェストには何も作りません**(出力先のディレクトリも作りません)。一時ディレクトリも残しません
- `--rebuild --dry-run --verify-content` では、タグに記録された内容の指紋との比較も表示します。違っても止めません(確認だけなので。本番の `--rebuild` は、違えば止まります)
- 確認に落ちたときは、本番と同じメッセージで止まります(終了コード 1)
- 実物の `wp dist-archive` が要ります(事前の確認で、無ければ止まります)。Zip を作るぶん、`--dry-run` だけより時間がかかります
- `--dry-run` と一緒のときだけ使えます(単独・`--list` と一緒は、使い方の誤りで終了コード 2)

### 事前の確認(`<slug> --dry-run`)

Zip もタグも作らずに、止めるべき状態がないかを確かめます。通常の実行(`<slug>`)と `--rebuild` も、同じ確認を先に行います。
次の順に確かめて、1 つでも当てはまれば止めます(終了コード 1)。

**版・`.distignore`・`check` は、作業ツリーのファイルではなく、Zip の元になる ref の内容から読みます**
(通常 = HEAD のコミット、`--rebuild` = タグの時点)。Zip に入る内容と、確かめる内容が同じになります。

| 確かめること | 止める条件 |
| --- | --- |
| 設定 | スラッグが設定にない / `requires` よりツールが古い / 大きさの上限の書き方の誤り |
| 道具 | `zip` コマンド・WP-CLI・`wp dist-archive` のどれかがない(入れ方を表示) |
| コミット | リポジトリにコミットがない |
| `--rebuild` のタグ | 版(指定がなければ HEAD の版)のタグがない |
| コミッター | (通常のみ)Git のコミッターの名前・メールが決まっていない(注釈付きタグを打てない) |
| 対象 | ディレクトリがない / ref の時点でコミット済みの `.distignore` がない |
| 作業ツリー | (通常のみ)未コミット・未追跡の変更がある。`--rebuild` は、タグの時点から作るので問わない |
| 版 | 版を読むファイルが ref にない / 版を読めない / 版がタグ名に使えない形(英数字で始まり、英数字と `. _ + -` だけ) / (`--rebuild`)タグの時点の版が、タグ名の版と違う |
| `check` | 食い違いがある(**すべて表示してから止める**。版の前後は英数字・`. _ + -` 以外であること: `1.2.3` は `11.2.30` や `1.2.3-beta` に一致しない) |
| タグ | (通常のみ)すでにある(`--rebuild` か版を上げる) |
| 出力先の Zip | すでにある(通常: タグがあれば「消してから `--rebuild`」、タグがなければ「作りかけの Zip が残っている」/ `--rebuild`: 上書きしない) |

止めずに警告だけ出すもの: ブランチが `main`/`master` でない・detached HEAD・出力先が Git の中で `.gitignore` にも入っていない。

`.distignore` が必須なのは、`wp dist-archive` が `.distignore` なしだと、`node_modules` や `src` を含む全ファイルを Zip に入れてしまうためです。

`WP_RELEASE_ZIP_MAKER_WP` に WP-CLI のパスを入れると、PATH 上の `wp` の代わりにそれを使います(複数の `wp` がある場合)。

### 配布してはいけないファイル(Zip を作ったあとの検査)

`.distignore` の書き忘れで、秘密の情報などが配布されないよう、作った Zip のファイル名を検査します。
**入っていれば、終了コード 1 で止め、Zip を消します**(タグも打ちません。`--rebuild` も同じです)。**例外はありません**(設定ファイルに許可の一覧を書くことはできません)。Zip に入れないものは、対象の `.distignore` に書いてコミットしてください。

- 名前: `.env`・`.env.*`(`.env.example` も)・`wp-config.php`・`id_rsa`・`id_ed25519`・`id_ecdsa`・`id_dsa`・`.htpasswd`・`.npmrc`・`.netrc`・`.git-credentials`・`.DS_Store`・`.wp-release`
- 拡張子: `.pem`・`.key`・`.p12`・`.pfx`(秘密鍵)/ `.sql`・`.sql.gz`・`.dump`(DB ダンプ)/ `.bak`・`.orig`・`.swp`・末尾が `~`(バックアップ・エディターの残り)
- パスの途中に `.git`・`.svn` のディレクトリがある

大文字小文字は区別しません。上に当たらない、ドットで始まるファイル・ディレクトリ(`.gitkeep`・`.eslintrc` など)は、**警告だけ**です。
`dir` の種類では、`.htaccess` と `.well-known/` は配布物であることが多いので、警告もしません。

検査するのは**ファイル名だけ**です(中身は見ません)。名前が一般的でない秘密のファイルは、検出できません。
`--dry-run` は Zip を作らないので、この検査をしません(Zip を作るときの検査です)。

### Zip の作り方(`<slug>`)

事前の確認が通ると、**HEAD の内容から**Zip を作ります(作業ツリーは使いません)。

1. `git archive` で、対象のディレクトリを一時ディレクトリの `<slug>/` へ展開します(未追跡・`.gitignore` で無視されたファイルは入りません)
2. `wp dist-archive` が、`.distignore` を適用して Zip にします。Zip の一番上のフォルダーはスラッグです
   (WordPress の管理画面からの上書きは、この名前で既存のものを置き換えるため). Zip は、まず**一時ディレクトリの中**に作ります
3. 作った Zip の中身を確かめます(すべてが `<slug>/` の下にあること・`<slug>/../x` のようにフォルダーの外へ出る名前(`..` の部品)が無いこと・配布してはいけないファイルが無いこと。下の「配布してはいけないファイル」)。失敗したときは、作りかけの Zip を消します
4. 確認した Zip を、出力先へ**上書きせずに**置きます(出力先と同じディスク上へコピーしてから、`ln` で最終の名前を作ります. すでに何か(壊れたシンボリックリンクを含む)あれば、置かずに止めます. 作っている間に別のプロセスが同じ名前のファイルを作った場合も同じです)
5. サイズ・SHA-256・ファイル数・直下の内訳を表示します

出力先のディレクトリが無ければ作ります。Zip の名前は `<出力先>/<slug>.<版>.zip` です。

知っておくこと:

- **`.gitattributes` の `export-ignore` が効きます。** `git archive` の仕様で、`.distignore` に書かなくても、それに合うファイルは Zip に入りません
- **設定ファイルが Git のルートの下にあっても動きます**(たとえば `app/public/.wp-release`。パスはそこからの相対パスで書きます)
- **プラグイン 1 つ型(パス `.`)では、`.wp-release` が対象の中に入ります。** `.distignore` に `.wp-release` と `.distignore` を書いてください(`.wp-release` が入っていると止めます)
- **ASCII 以外(日本語など)のファイル名がある場合は、警告します。** `zip` コマンドが「UTF-8 の名前」の印を付けないため、展開する環境によっては文字化けします。
  テーマ・プラグインのファイル名は英数字にするのが無難です
- `.distignore` の `**/*.log` は、ルート直下の `a.log` に当たりません(深い階層にだけ効きます)。ルート直下も除くなら `*.log` と書きます
- 表示される内訳は、ASCII 以外のファイル名を `?` にして出します(macOS の `unzip` の出力が、そのバイトを落とすため)

### タグ(`<slug>`)

Zip を作れたら、HEAD のコミットに**注釈付きタグ**を打ちます。**push はしません**(共有するなら、表示されるコマンドを自分で実行します)。
タグ名は `tag_format` で決まります(版は素の番号で、`v` を付けません)。

タグのメッセージには、次を記録します。

```text
my-plugin 1.2.3

Zip: my-plugin.1.2.3.zip
SHA-256: <配布した Zip そのもの(バイト列)の SHA-256>
Content-SHA-256: <Zip の内容の指紋>
Built-with: wp-release-zip-maker 1.1.0
WP-CLI: 2.12.0
dist-archive: 3.1.0
zip: 3.0
```

- `SHA-256` は、**配布した Zip の現物**が、このタグのものと同じかを確かめるための記録です(`shasum -a 256 <Zip>` と比べます)
- `Content-SHA-256` は、Zip の**内容の指紋**です。Zip を一時ディレクトリへ展開し、通常のファイルは「パスと内容の SHA-256」、実行権限のあるファイルは「パス」、シンボリックリンクは「パスとリンク先」の行を並べ替えて SHA-256 にしたものです(時刻・圧縮のしかた・空のディレクトリを含みません)。
  ファイルの内容そのものを SHA-256 にしているので、CRC-32 のように「同じ値になる別の内容」を作られる心配はありません。
  `--rebuild` が、作り直した Zip の内容と比べるのに使います。必ず書きます(Zip を展開できなければ、タグを打たずに止めます)
- `WP-CLI`・`dist-archive`・`zip` は、**Zip を作ったときの道具の版**です(`wp --version`・WP-CLI のパッケージの記録・`zip -v` から読みます)。調べられなければ `unknown` と書き、Zip の作成は続けます。
  `--rebuild` で内容が違ったとき、この記録と今の版を並べて、道具の版が変わったのかをたどれるようにするためのものです。
  `dist-archive` の版は、`wp package path` で調べた場所の `vendor/composer/installed.json` から読みます(この Mac で 1 回 0.13 秒)。
  読めなければ `wp package list` で読みます(1 回 1.5〜2.1 秒)。どちらも同じ記録が元なので、書かれる値は同じです(WP-CLI 2.12.0 のソースで確認)
- タグを打てなかったとき(`gpg` の署名の失敗など)は、作った Zip も消します(「タグの無い Zip」を残さないため)

### 署名付きのタグ(`--sign`)

`--sign` を付けると、`git tag -s` で**署名付きの注釈付きタグ**を打ちます(`gpg` と、署名する鍵が要ります)。

```text
wp-release-zip-maker my-plugin --sign
git tag -v my-plugin/1.2.3        # 署名の確認(Git の標準の機能)
```

- 署名は Git と `gpg` に任せます。このツールは鍵を扱いません。署名する鍵は、`git config user.signingkey`(未設定なら、コミッターの名前・メールに合う鍵)で決まります
- **署名できなかったとき**(`gpg` が無い・鍵が無い・パスフレーズの入力に失敗など)は、タグを打たず、Zip(と `--manifest` のマニフェスト)も消して、終了コード 1 で止めます。止めるときのメッセージに、確かめる点を出します
- `--sign` は、タグを打つ通常の実行でだけ指定できます(`--rebuild` はタグを打たないので、使えません。`--list` とも組み合わせられません)。`--dry-run` と組み合わせると、署名する予定だと表示します(実際には署名しません。署名できるかは、実際に打たないと分かりません)
- **`--sign` を付けなくても**、`git config tag.gpgSign true` にしていれば、Git が(`git tag -a` でも)署名します。毎回署名したいときは、こちらの設定が楽です
- 署名したのは**タグ**(コミットと、メッセージに記録した SHA-256・内容の指紋)です。配布する Zip そのものへの署名は、このツールでは作りません。受け取る側は、Zip の SHA-256 または `--manifest` のマニフェストを、署名で保護されたタグの記録と照合してください
- **実際の `gpg` での署名は、開発した環境に `gpg` が無く、検証していません**(テストは、Git が期待する形を返す偽の `gpg` で、ツールの動作を確かめています)。初めて使うときは、先にテスト用のリポジトリで試してください

### `--rebuild`(既存のタグから Zip だけを作り直す)

Zip をなくしたときや、同じ版の Zip を作り直したいときに使います。**タグは打ちません。**
作業ツリーが汚れていても動きます(タグの時点のコミットから作るため)。

```text
wp-release-zip-maker my-plugin --rebuild           # HEAD の版のタグから
wp-release-zip-maker my-plugin --rebuild 1.2.3     # 版を指定する(版を進めたあとに、前の版を作り直すとき)
```

- 出力先に同名の Zip があれば止めます(上書きしません。確かめて消してから実行します)
- 終わると、作り直した Zip の**内容の指紋**を、タグに記録された `Content-SHA-256` と比べて表示します。
  一致すれば、元の Zip と同じファイル・同じ内容です。
  **違えば、終了コード 1 で止めます**(作り直した Zip は消します。そのままアップロードされないためです)。`.distignore`・`zip`・`wp dist-archive` の版などで、入るファイルが変わった可能性があります。
  意図した違いなら、`--allow-content-change` を付けると、警告を出したうえで続けます(`--rebuild` のときだけ指定できます)
  違うと分かったときは、Zip を作った道具の版を「タグの記録 → 今回」で並べて表示し、違うものに印(`← 違います`)を付けます。すべて同じなら、そう伝えます。旧タグ(版の記録がない)は「(記録なし)」と表示します
- **Zip 全体の SHA-256 は、同じコミットから作り直しても毎回変わります**(`zip` が時刻などの属性を入れるため)。
  そのため、作り直した Zip の SHA-256 とタグの記録は一致しません。これは正常です。配布した Zip の現物を照合するときは、その Zip の SHA-256 をタグに記録された `SHA-256` と比べてください
- タグが、このツールで打ったものでない(`Content-SHA-256` がない)ときや、Zip を展開できず指紋を計算できないときは、比べようがないので、止めずに「中身を目で確かめてください」と表示します

### `--manifest`(Zip の内容のマニフェスト)

`--manifest` を付けると、Zip と同じ出力先に **`<slug>.<版>.manifest.txt`** を作ります(通常の実行・`--rebuild` のどちらでも)。
Zip の中のファイルごとに、`<SHA-256>` と、Zip の一番上のフォルダーからのパスを並べたものです(`shasum -a 256 -c` が読める形)。

```text
3b0c…(64 桁)  my-plugin/my main.php
a7f1…(64 桁)  my-plugin/assets/app.js
```

- 展開した Zip(またはサーバーに置いたディレクトリ)の**親のディレクトリ**で `shasum -a 256 -c <マニフェスト>` を実行すると、中身が同じかを照合できます(1 つでも違えば失敗します)
- 内容の指紋(`Content-SHA-256`)と**同じデータ**から作るので、両者は食い違いません。ただし、マニフェストには実行権限とシンボリックリンクは載せません(指紋には入っています)。ディレクトリも載せません
- **上書きしません。** すでにあれば、Zip もタグも作らずに止めます(`--dry-run` でも確かめられます)。タグを打てなかったときは、Zip と一緒に消します。`--rebuild` で内容の指紋が違って止めるときは、作りません
- Zip を展開できなければ、マニフェストを作れず、Zip も消して止めます
- 付けなければ作りません(出力先のファイルが増えるため、既定では作らない設計です)

### アップロードの手順(Zip を作ったあとに表示)

Zip を作った(作り直した)あとに、サーバーへ上げる手順を表示します(`--dry-run` では表示しません)。

- **`theme` / `plugin`**: 管理画面の Zip アップロードで上げます。Zip の一番上のフォルダー(スラッグ)が、置き換わる対象を決めます
- **`dir`**(WordPress の外のディレクトリ): SSH の手順を、版・スラッグ・Zip のパスを埋めて表示します

`dir` の手順の考え方:

- **上書きで展開しません。** 新しいディレクトリへ展開してから差し替えます(新しい版で消したファイルが、サーバーに残らないように。管理画面の Zip アップロードと同じ結果にします)
- **旧版は docroot の外(`~/releases`)へ退避します。** docroot の中に置くと、古い版が URL で見えてしまいます。退避先は `<slug>.bak-<前の版>` で、前の版は**同じスラッグの 1 つ前のタグ**から求めます(版は数の並びで比べます: `1.9.0` の次が `1.10.0`)。前のタグが無ければ `<slug>.bak` です
- **戻すときのコマンドも表示します**(失敗した版を `<slug>.failed-<版>` へ退避して、旧版を戻す)
- **配置先・退避先がすでにあるときは、何も動かしません。** 手順の先頭で、`~/releases/<slug>.<版>`・その展開の途中用の `.partial`・退避先(`<slug>.bak-<前の版>`)・`<slug>.failed-<版>` の 4 つを確かめ、あれば「すでにあります」と表示します。
  そのうえで、展開(`mkdir ... && unzip`)・退避・差し替え・戻すの各コマンドも、行き先がすでにあれば動かず、そのことを表示します(`mv` が行き先のディレクトリの中へ入れ子で入れる事故と、古いファイルが混ざる事故を防ぐため)。
  手順を 1 行ずつ貼り付けても使えるよう、`exit` は使っていません
- **展開に失敗したら、docroot の旧版を動かしません。** まず `<slug>.<版>.partial` へ展開し、全部成功したときだけ `<slug>.<版>` に名前を変えて、変数 `EXTRACTED=1` を立てます。退避・差し替えのコマンドは、それが立っていなければ「展開が済んでいない」と表示して動きません(Zip が壊れていたり、途中で切れていたりしても、旧版が docroot から消えたまま、新しい版も置けない状態になりません).
  この判定はシェルの変数なので、手順を同じシェルで続けて実行(貼り付け)することが前提です
- **表示するコマンドの Zip のパスは、シェル用にクォートします**(空白・`;`・`'`・`"`・`$()`・バッククォートなどを含む出力先でも、`scp` に 1 つの引数として渡り、コマンドとして実行されません)
- `df ~/releases "$DOCROOT"` で、同じディスクか確かめます。別のディスクだと `mv` がコピーになり、その間ページが無くなります
- `unzip` が無いサーバー向けに、`php -r` で展開する 1 行も表示します
- Zip に `VERSION` が入っていないとき(`.distignore` で除いている)は、サーバーで版を確かめる行を省き、警告します
- `user@host` と `/path/to/public_html` は、自分の環境に置き換えます。サーバーの手順は 1 行ずつ確かめながら実行してください

注意: `tag_format` が `{version}` だけのとき(対象が 1 つのリポジトリ)は、リポジトリのすべてのタグが「前の版」の候補になります。
数字で始まるが版ではないタグ(`2024-01-backup` など)があると、それを前の版と見なすことがあります。

### 版の読み方

| 種類 | 版を読む場所 |
| --- | --- |
| `theme` | `style.css` の `Version:`(先頭 5000 バイト) |
| `plugin` | 直下の `*.php` のうち `Plugin Name:` を持つ最初のファイル(Git の名前順)の `Version:`(先頭 8192 バイト) |
| `dir` | `VERSION` ファイルの 1 行目 |

`--list` は作業ツリーのファイルから、Zip の作成・`--rebuild` は ref(HEAD・タグ)の内容から読みます。

### `--list`

設定にある対象と、今の版(作業ツリーのファイル)・タグの有無を一覧にします。

```text
KIND    SLUG        VERSION    TAG                 TAGGED PATH
plugin  my-plugin   1.2.3      my-plugin/1.2.3     yes    wp-content/plugins/my-plugin
theme   my-theme    0.1.0      my-theme/0.1.0      no     wp-content/themes/my-theme
dir     lp          2.0.0      lp/2.0.0            no     lp
```

ディレクトリが無い・版を読めない対象は、`?` を付けて一覧に残します(終了コードは 0)。
設定の形式の誤りは、行番号つきで止めます(終了コード 1)。

## 開発・テスト

テストは bash だけで書いてあります(外部のテストツールは要りません)。

```bash
tests/run.sh                   # 速いテストだけ(shellcheck を含む. 約 30 秒)。実物の WP-CLI が要るテストは飛ばす
tests/run.sh --all             # すべて(実物の WP-CLI で Zip を作るテストも. 約 2 分半)
tests/run.sh --list            # 流さずに、ファイルごとのテストの数・実物の WP-CLI が要る数・目安の時間を一覧にする
tests/run.sh preflight         # ファイル名に 'preflight' を含むファイルだけ
tests/run.sh --all zip rebuild # そのファイルの中で、テスト名に 'rebuild' を含むものだけ(--all はどこに書いてもよい)
tests/run.sh lint              # shellcheck だけ
tests/run.sh --help            # 使い方
```

- **すべてのテストには時間がかかります。** そのため、引数なしでは速いテストだけを流し、実物の WP-CLI が要るテストは飛ばします。
  絞り込みで重いファイルを名指ししても、`--all` が無ければ飛ばします。最後に、飛ばした件数と `--all` の案内を必ず表示します
- **リリースの前(版を上げる前)には、必ず `--all` を流してください。** 引数なしの「すべて成功」は、重いテストを飛ばした結果です
- 始める前に、対象のファイルの数と目安の時間を表示します。各ファイルの集計行と最後の結果に、かかった時間を出します

時間は、2026-10-28 のこの Mac での実測です(`--all`. 目安は `tests/run.sh --list` でも見られます)。

| --- | --- | --- | --- | --- |

| Zip の作成と確認(`make_zip`・`publish_zip`・`verify_zip`・`scan_zip_names`・マニフェスト) | `tests/run.sh --all zip` |
| タグ(`create_tag`・道具の版の読み方)・`--rebuild`・内容の指紋 | `tests/run.sh --all tag_rebuild` |
| アップロード手順(`print_deploy_hint`・`previous_version`・`shell_quote`) | `tests/run.sh --all deploy_hint` |
| どこを直しても | `tests/run.sh lint`(shellcheck) |

### そのほか

- ケースは `tests/cases/` にあります。共通部品は `tests/lib.sh` です
- テストは一時ディレクトリの中だけで動きます。Git の設定(`GIT_CONFIG_GLOBAL`)と `TMPDIR` をテスト用に差し替えるので、実行する人の環境に結果が左右されません
- 必要なもの: git 2.32 以上・unzip。**Zip を実際に作るテストは、実物の `wp dist-archive` と zip が無ければ SKIP になります**
  (事前の確認のテストは、偽の `wp` で動くので、実物が無くても通ります)
- shellcheck が無ければ、その検査は SKIP になります
- 環境変数 `WRZM_BASH` でツールを動かす bash を、`WRZM_TOOL` でテストするツールを差し替えられます。
  既定の `/bin/bash` は、macOS では 3.2 なので、bash 3.2 互換の確認になります
- dir の SSH の手順は、表示されたコマンドを疑似サーバー(別ディレクトリ・偽の `HOME`)で**実際に実行して**確かめています
- 新しい不具合を直したときは、先にそれを再現するテストを足してください(これまでに実際に踏んだ不具合は、すべてテストにしてあります)
